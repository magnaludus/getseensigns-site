# Get Seen Signs website: build source

The site is a static site generated by Python. The built pages live at the repo root
(index.html, product folders, blog, 404.html, privacy.html, sitemap.xml, robots.txt).
Cloudflare Pages publishes `main` automatically about a minute after every merge, so a merge is the publish step.

## Files

| File | What it holds |
|---|---|
| `src/seo_products.py` | Product page copy, FAQs and the "from" prices (`price=`). `price=None` shows no price and adds no Offer. Optional per product: `etsy='<listing id>'` (leave it out for a product with no Etsy listing, like `custom-patches`: the page then has no Etsy links and its Offers point at its own page), `videos=[(file, label)]` (files in `assets/video/NN-name.mp4` plus `NN-name-poster.jpg`, embedded muted with a poster and `preload="none"`), `gallery_extra=[(image base, alt)]`, and `turnaround='...'` with `handling=(lo,hi)`, `transit=(lo,hi)` for products that do not use Etsy's standard "Arrives 3-8 business days after proof approval; tents and backdrops 5-10 business days." |
| `src/seo_pages.py` | Local landing pages, blog posts and the gameday page. |
| `src/site-src-index.tpl.html` | Home page body (between `<main>` and `</main>`). |
| `src/site-src-pages.py` | Builds every HTML page, sitemap.xml, robots.txt and 404.html. Shared head, nav, footer and the shipping schema (`shipping_details`, `TRANSIT`, `RETURNS`). |
| `src/design_catalog.json` | Designer products, option groups, fonts, palettes and scenes. Prices are not stored here. |
| `src/order_catalog.py` | Self-serve ordering: maps every product page's options to a saved Stripe SKU and writes `assets/order/catalog.json`. The build stops if a price disagrees with `functions/_lib/catalog.js` or a priced option has no SKU. |
| `assets/order/` | The order panel (`order.js`, `order.css`) and the generated `catalog.json`. |
| `src/design_catalog.py` | Builds `assets/design/catalog.json`, `print-specs.json` and `templates.json`. Copies each option's price from `seo_products.py` `offer_rows`; the build stops if an offer string does not match, a combination has no price, a template uses a blocklisted name, or a sample phone number is not a 555-01xx number. |
| `src/design_print_specs.json` | True artwork sizes in inches for every product and option. Each row has a `source` or a status (`TODO_SPEC` or `UX_DEFAULT`). |
| `src/design_templates/*.json` | The 20 starting layouts (4 per product). Fictional sample words only. |
| `src/design_blocklist.txt` | Names that must never appear in a template or in the designer's wording. |
| `src/design_pages.py` | Titles, descriptions, headings, copy and FAQs for `/design/` and the ten `/design/<product>/` pages. |
| `assets/design/` | The designer: plain ES modules and CSS, no build step. `vendor/three.module.min.js` (Three.js, MIT) loads only when the 3D view opens. `catalog.json`, `print-specs.json` and `templates.json` are generated. |
| `functions/api/design-proof.js`, `functions/api/design-event.js` | Pages Functions for proof requests (on once `DB` and `BREVO_API_KEY` exist, or the older R2 setup is flagged on) and anonymous usage counts (off unless its flag is `true`). |
| `functions/proof/`, `functions/order/`, `functions/api/admin/`, `functions/api/stripe-webhook.js`, `functions/_lib/`, `admin/` | Store checkout: proof approval, Stripe Checkout, webhook, tracking, order emails (not generated by the Python build). See the root `README.md`. |
| `src/tools/design_events_report.py` | Summarises exported usage events. Not deployed. |
| `src/tools/make_responsive_images.py` | Makes the phone-size home hero images (`hero-*-480/768/320.webp`) and the WebP video posters (`assets/video/*-poster.webp`) from the full-size files. |
| `src/tools/make_patch_placeholders.py` | Draws the stand-in Custom Patches images (`p-19-custom-patches.*`, `g-19-custom-patches-2.*`) in the brand colors. Replace those files with real photos when they exist. |
| `.design-dev/` | Tests, screenshots, Lighthouse runner and the Three.js vendor build. Not deployed (the deploy skips dot-directories). See `.design-dev/README.md`. |
| `assets/style.css` | CSS source. It is inlined into every page at build time, so a style change needs a rebuild. |
| `assets/` | Images, fonts (Barlow, OFL) and brand files, already built. |

## Build

```
pip install pillow
git pull origin main
python3 src/site-src-pages.py
```

Run it from anywhere; paths are relative to the repo root. Output is written to the repo root.
The sitemap `lastmod` (for pages without an explicit date) and the blog `dateModified` use today's date in America/New_York at build time. Set `BUILD_DATE=YYYY-MM-DD` to fix it, for example `BUILD_DATE=2026-10-28 python3 src/site-src-pages.py`. Nothing else in a page depends on the date, so a rebuild on a new day only changes `sitemap.xml` and the four blog pages.
Then check `git diff`: only the pages you meant to change should differ.

## Checklist before every PR

- Keep the canonical tag (`https://getseensignsco.com/<slug>/`, https, bare domain, trailing slash) on every page.
- Keep `shippingDetails` (free shipping, destination US limited to the 48 lower states by `addressRegion`) and `hasMerchantReturnPolicy` (MerchantReturnNotPermitted) on every Offer. Every Offer `url` is the product's own page, never an Etsy listing.
- Site prices must match the live Etsy prices. Change Etsy first, then `seo_products.py`, then rebuild.
- No trademarks: keep the line that buyers own the artwork they send and we don't print team names or logos.
- Keep the sitemap entry and breadcrumb for every page. Keep `privacy.html`, `terms.html` and `contact.html` as the file names (they serve at /privacy, /terms and /contact). Terms and privacy body copy comes from `src/legal/terms.md` and `src/legal/privacy.md`. Do not reword that copy.
- Never hand-edit a built page; the next rebuild overwrites it. Edit `src/` and rebuild.
- Nothing private goes in this repo: no costs, margins, supplier names or quotes, passwords, tokens or account details.

## Online designer (`/design/`)

Customers pick a product, pick a template, change the words, colors and font right on the picture, add a logo, turn the product around in 3D, and send a free proof request. The preview is not a print file and there is no checkout. Nothing prints until they approve the real proof (within 12 hours, 7 days a week, 3 revisions).

`/design/` is a plain list of the ten products. Each product has its own page, `/design/<slug>/`, where the editor loads: `canopy-tent`, `feather-flag`, `yard-signs`, `table-throw`, `vinyl-banner`, `retractable-banner`, `step-and-repeat`, `car-magnet`, `hard-hat-decal`, `safety-sign`. A link like `/design/vinyl-banner/?size=3x6&material=18oz&qty=2` opens the designer with those choices (the order panel builds these). Old `/design/?product=<id>` links redirect to the right page. A link with `#d=...` opens a shared design (those pages are marked `noindex`).

Sample words in the templates are fictional, phone numbers are 555-01xx, and web addresses use `name.example`. Do not put real team, school, league or brand names in them; the build stops if one from `src/design_blocklist.txt` appears.

### Change something

- **Prices.** Never here. Change Etsy first, then `seo_products.py`, then rebuild. Every option's price on the designer page comes from the matching `offer_rows` string, and the server recomputes the total from the same catalog.
- **A template.** Copy a file in `src/design_templates/`, change the words, fractions and colors, and add its id to the product's `templates` list in `src/design_catalog.json`. Boxes are fractions of the product's regions (`art`, `trim`, `safe`, plus `peak`, `valance`, `valancebar` and `roofarea` on the canopy and `head`, `body` and `foot` on the feather flag; the canopy and flag blocks are sized from the printer's outline, so the flag's head keeps right of the curved top and its foot keeps left of the slanted bottom). Text can be `fit` to a box and `bind` to the customer's name, second line, phone or web address.
- **A print size or guide.** Edit `src/design_print_specs.json`. Every row has a `source` or a status. A source of `printer template` means the printer's published template or spec page. Do not write printer names or links in this file: the repo must not name suppliers, and the build stops if it finds a link. `UX_DEFAULT` rows are our own design choices (minimum letter heights, DPI colors, grommet spacing, the yard sign ground line and safe inset). `TODO_SPEC` marks a placeholder, and the editor tells the customer some guides are approximate while any exist; none are left today.

  The canopy roof (`roof.points`), the three flag outlines (`outline.points`) and the table throw panels (`panels_in_template`) are the printers' own outlines and boxes, in inches, origin at the top left of the artboard. The flag artboard is the flag's own size and `outline.template_page` keeps where it sits on the printer's page, for print files. A safe line marked `outline_inset` follows the cut outline (2 in inside it) instead of being a rectangle. The table throw has one entry per length and style (`6-3`, `6-4`, `8-3`, `8-4`) because the front panel differs a little between 3-sided and 4-sided. Not published by the printers, so not in the data: the flag sleeve width (`pole_sleeve.width_in` is null and the 3D picture guesses), a safe inset for the second yard printer (we keep 1 in, our own choice), and the canopy's own safe-line corner points (the editor moves the cut outline in 2 in, which lands on the printer's box within 0.15 in).

  Order choices, not printer numbers: we sell the sleeve-left flag only (no reverse flag, so only that outline is stored), and yard signs are ordered with vertical flutes, parallel to the 18 in side of the 24 x 18 sign, so the H stake slides in from the bottom. The 3D yard sign draws the flutes that way, and the build stops if `flutes.direction` is set to something it does not draw.
- **A product.** It needs offer rows in `seo_products.py`, an entry in `src/design_catalog.json`, a print spec, templates, an entry in `src/design_pages.py` and a 3D model in `assets/design/three/models/`.
- **Quantity.** Yard signs are fixed packs (5 to 100). Everything else allows 1 to 20 and the total is the listed price times the count; multi-buy discounts are not modelled. Rush and bundle discounts are switched off in the catalog (`rush.enabled`, `bundles.enabled`) until Scott sets them.

### What the page does when it loads

The first paint needs the page HTML, one stylesheet (inlined) and about 80 KB of gzipped modules. Three.js, the product models and the scenes are fetched only when the customer opens the 3D view (the code is fetched a moment earlier if they point at or touch the 3D button). If WebGL is missing, the phone is short on memory, or the 3D view takes more than 4 seconds to start, the page shows a flat "simple view" instead and says so. Editing and sending a proof never depend on 3D.

### Scenes

The 3D view has three scenes: `studio` (a plain sweep, drawn in code), `yard` (a front lawn) and `storefront` (a strip-mall plaza). `yard` and `storefront` are photos. The product turns on an invisible floor in front of the photo and the floor catches its shadow; the camera can tilt from 3 to 30 degrees. If a photo fails to load, the drawn version of that scene shows instead.

To add or replace a photo:

1. Save it twice as `assets/design/scenes/<name>-2048.webp` and `assets/design/scenes/<name>-1024.webp` (long edge exactly 2048 and 1024 px, 3:2 landscape, WebP, sRGB, no transparency). Phones load the 1024 file and desktops the 2048 file.
2. In `src/design_catalog.json`, set the scene's `"plate"` to `"<name>"`.
3. Add a one-line credit to `assets/design/scenes/CREDITS.md`.
4. Rebuild. The build stops if a named photo file is missing.

The current 2048 files are 2x upscales of the 1024 photos, because no larger originals exist. Swap in sharper originals when there are some. Prompts for new photos, and what a good one looks like, are in `.design-dev/scene-plate-prompts.md`. The three Phase 2 scenes in the spec (`range`, `gunshow`, `ballfield`) need a drawn version or a photo before they can be listed in `design_catalog.json`.

### Sending a proof request

The form posts to `POST /api/design-proof` (the design as JSON, the customer's details, a preview PNG per side and any logo files). Until that function is switched on it answers 503 and the page uses the fallback, which needs no server:

- It downloads `getseen-design-GS-XXXXXXXX.zip` with the previews, the design file, the logo and a plain-text summary.
- It opens a `mailto:sales@getseensignsco.com` message with the summary and the same `GS-XXXXXXXX` reference.
- The customer attaches the zip. Browsers cannot attach files to a mailto link for them.

"Rather have us design it" sends only the short form (the wording, the products and a link to their website or logo).

### Turn on the Pages Function

Do this in the Cloudflare account that already hosts the site. Do not create a new service, and do not put secrets in the repo. Leave it off and the site still deploys; the mailto path keeps working.

**Recommended: D1 + Brevo (the same database and mail account the store checkout uses).** Nothing new to buy, no R2, no Email Routing.

1. The orders D1 database must be bound to the Pages project as `DB` (Settings → Bindings → D1 database; see the root `README.md`). The two new tables are created automatically on first use. To create them by hand instead, run `migrations/0002_design_proof_requests.sql` (`wrangler d1 execute getseensigns-orders --remote --file=migrations/0002_design_proof_requests.sql`).
2. `BREVO_API_KEY` must be set as a secret in Pages → Settings → Environment variables, with `sales@getseensignsco.com` verified as a Brevo sender.
3. Redeploy (a merge to `main` does that). No other variable is needed: the function turns itself on when both `DB` and `BREVO_API_KEY` exist.

`DESIGN_PROOF_ENABLED` is optional: `false` forces the function off (the page uses the mailto path), `true` forces it on, anything else or unset means "on when `DB` and `BREVO_API_KEY` are both present".

What happens to a request: it is saved in D1 (`design_proof_requests`: the request fields, the design JSON, the file list with sizes and SHA-256 hashes, and the email status; no IP, cookie or user agent), and emailed through Brevo to `sales@getseensignsco.com` from "Get Seen Signs <sales@getseensignsco.com>" with Reply-To set to the customer, the previews first and then the logos attached while they total under 3 MB. Files that did not fit are saved in D1 (`design_proof_files`, base64 chunks of 256 KB, up to 10 MB per request) and the email says so; anything beyond that is only listed, with a note to ask the customer to reply with it. The customer gets a short confirmation email with the reference and the 12-hour promise. The page shows success only when the email to the shop went out; if Brevo is down the request is still saved, and the customer sees the mailto fallback with their reference. Read requests back with `GET /api/admin/design-proofs`, `GET /api/admin/design-proofs/<ref>` and `GET /api/admin/design-proofs/<ref>/<file>` (bearer `ADMIN_TOKEN`).

**Older option: R2 + Email Routing (still supported, not required).**

1. Create a private R2 bucket, for example `getseen-design-proofs`. Do not turn on public access or r2.dev.
2. Pages project → Settings → Bindings → add an R2 bucket binding. Variable name: `PROOFS`.
3. Optional email, using Cloudflare Email Routing on `getseensignsco.com`: verify the destination mailbox, add a `send_email` binding named `SEND_EMAIL`, and set `DESIGN_PROOF_TO` and `DESIGN_PROOF_FROM` (an address on this domain Email Routing can send as). This clashes with an existing MX setup on the domain, so use Brevo instead if the domain's mail is hosted elsewhere.
4. Set `DESIGN_PROOF_ENABLED` = `true` and redeploy.

With R2 bound, every file is stored there at `design-proofs/YYYY-MM-DD/<ref>/` (`design.json`, `preview-<n>.png`, `logo-<n>.*`, then `request.json` last, so a folder without it is a failed upload), and D1 (if bound) keeps only the request. If both Brevo and `SEND_EMAIL` are set, Brevo is tried first and `SEND_EMAIL` is the fallback (that message attaches under about 1.5 MB). Without any email route the request is stored and the function answers `emailed: false`.

When the function is off, `POST /api/design-proof` returns `{"ok":false,"enabled":false}` with status 503. When it is on, it checks every field, recomputes the price from the catalog, and sanitizes SVG logos before they are stored or attached. The storage holds customer names, emails, phone numbers and artwork: keep the bucket private and the D1 database unbound from anything public. The function allows 8 requests an hour per address, counted in memory on each server instance (the address is never stored); add a Cloudflare WAF rate-limiting rule on `/api/design-proof` if you want a hard limit.

### Usage counts (off)

`functions/api/design-event.js` collects anonymous event counts (designer started, template used, 3D opened, proof sent, errors) with no personal data. It is off in two places and both must be turned on: `DESIGN_EVENTS_CLIENT` near the top of the design section in `src/site-src-pages.py` (set it to `True` and rebuild so the pages send events) and `DESIGN_EVENTS_ENABLED` = `true` in Pages environment variables (the function stores them in the same `PROOFS` bucket under `events/`). To read them, download the `events/` folder and run `python3 src/tools/design_events_report.py <folder>`.

Work on a branch, commit the source and the rebuilt pages together, and open a pull request against `main`.
Never push to `main` directly. Merge (squash) only after Scott says yes in chat.
